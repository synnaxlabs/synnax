# 46 (companion) - Implementation Plan

Companion to RFC 0046 (`0046-260716-client-cache-unified-reads-session-state.md`). The
RFC owns the design; this document owns the execution: what moves where, the public API
of each package, data-structure responsibilities, and how each package is tested. Every
referenced symbol was read at the cited location; everything marked NEW names its
precedent.

# 0 - The Seams

Three seams carry the whole program:

1. **client/ts cache <-> flux bindings.** The cache subsystem (stores, streamer loop,
   epochs, tombstones, query lifecycle) is framework-free and lives in `client/ts`. Flux
   consumes it exclusively through each domain client's three read members
   (`retrieve`/`onChange`/`getCached`, RFC §5.1a); stores, query entries, and tombstones
   are never visible above the domain client. Zero deep imports of `@/flux/base` exist
   outside flux itself, so the move breaks exactly three barrels
   (`flux/base/external.ts`, `flux/aether/external.ts`, `flux/external.ts`) plus the
   factory files.
2. **Engine <-> domain clients.** Inside `client/ts`, a pure-mechanism core engine is
   injected into each domain client in the `Synnax` constructor
   (`client/ts/src/client.ts:117-193`, sub-clients at 137-186). The domain client binds
   its store config to the engine and exposes the typed surface. Precedent: the flux
   `Client` already composes stores from an injected `StoreConfig`
   (`pluto/src/flux/base/client.ts`).
3. **Session convergence <-> persistence partitions.** Reducers own repair; a
   synchronizer-hook registry (precedent: `Link.Registry`,
   `console/src/platform/link/types.ts:40`, merged at `app/link/useDeep.ts:23`, mounted
   `Primary.tsx:34`) covers live events and epoch sweeps. The persist layer owns context
   scoping via key-prefixed partitions; no reducer or reconciler is ever cluster-aware.

# 1 - Go Core: Delete Signal Channels (opening move)

Schematic, lineplot, log, and table have `sy_<x>_set` but no `sy_<x>_delete`. Add the
four delete channels following the existing signal-channel pattern used by the domains
that have both (e.g. ranger). Lands first, alone: additive, no wire-format change,
unblocks uniform cache deletion without an ontology-derived backstop (rejected in the
interview). Verify with a live-core spec per channel: delete through client A, observe
the signal through a raw streamer.

# 2 - Package: `client/ts` Cache Subsystem

## 2.1 - Module layout

New top-level `src/cache/` (namespace rule: `cache.Engine`, `cache.Store`, never
`cache.CacheStore`), exported through `src/index.ts` like every existing module. No
package subpath needed; the surface rides the root export.

## 2.2 - Move manifest (from `pluto/src/flux/base/`)

| Source                                                                                                                                                                           | Disposition                                                                                                                                                 |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `store.ts` (`ScopedUnaryStore`, `createStore`, `scopeStore`, `StoreConfig`, `UnaryStoreConfig`, `ChannelListener`, `SetHandler`/`DeleteHandler`, `partialUpdate`, `orderByKeys`) | Moves, internal-only. Gains the tombstone map; deletion surfaces solely through `onChange`/`getCached`.                                                     |
| `streamer.ts` (`openStreamer`, `channelNameSort` delete-first ordering)                                                                                                          | Moves. Gains lazy-open (opens on first cache demand) and epoch surfacing.                                                                                   |
| `client.ts` (`Client`, `getCache`, `caches` map, `scopedStore`, `awaitInitialized`, `close`)                                                                                     | Becomes the engine. Loses flux naming; gains reconciliation.                                                                                                |
| `queryCache.ts` (`QueryCache`, `hashQuery`)                                                                                                                                      | Moves, shrunk to lifecycle only (promise dedup, loading/error). Store events drive transitions; reconciliation never touches it.                            |
| `types.ts` (`Query`, `FetchOptions`, `Verbs`)                                                                                                                                    | Moves.                                                                                                                                                      |
| `undoable.ts` (`UndoableUnaryStore`, `createUndoableStore`, `DispatchFrame`, 500ms coalesce, stackCap 200)                                                                       | Dissolves. Stacks and dispatch bookkeeping become a dispatch subsystem beside `client/ts/src/actions/`, operating on plain stores.                          |
| `result.ts` (flux root)                                                                                                                                                          | Stays in flux. `promise`/`name` hooks and `pendingResult` are deleted; the query lifecycle defines its own internal entry state. `Result` is mutation-only. |

Absorbed and deleted: `channel.CacheRetriever` (the existing in-client cache precedent);
its callers read through the channel domain client's cache instead.

## 2.3 - Public API

Per-domain, on each domain client (NEW, RFC §5.1a/5.1b). The whole read surface is three
members; there is no `store` getter, no dispatcher getter, and no public tombstone or
query-cache type:

```ts
// e.g. client.ranges.retrieve / onChange / getCached
retrieve(query): Promise<Data>;             // signature unchanged; cached + deduped
onChange(query, handler): destructor.Destructor;
getCached(query): Cached<Data> | undefined; // sync, no promise

type Cached<Data> =
  | { variant: "changed"; data: Data }
  | { variant: "deleted"; corpse: Data };   // corpse never appears as bare Data
```

Writes stay on the domain clients' existing mutation methods, gaining options (undoable,
transaction) where console needs control; write-through + rollback relocate from flux
`createUpdate` internals. Undoable domains add `undo(key)` / `redo(key)`; undo entries
carry their domain so a future global `client.undo` can delegate. Scope-qualified
entries and writer-scope suppression carry over unchanged from `ScopedUnaryStore`, as
internals.

Client-level (NEW):

- `synnaxParamsZ` gains `cache?: boolean` (default true), sibling of the existing
  `retry` slot. Opt-out constructs domain clients with no engine binding: retrieves go
  straight to the network, no stream ever opens.
- `client.cache: cache.Handle` exposing
  `onEpoch(cb: (epoch: number) => void): destructor.Destructor` (x `observe.Observer`
  underneath) and `enabled`. This is cache control surface, not a data path; the three
  per-domain read members remain the only data access path.

Engine (internal, injected, never exported from the package root):
`registerStore(config)`, the streamer loop, epoch counter, `reconcile()` (bulk
existence-check of cached keys, tombstone vanished, refresh changed), query lifecycle.
Bulk existence checks ride the existing partial-return array retrieves (ranger,
ontology, label, channel already return partial results without throwing; single-key
throws stay confined to `checkForMultipleOrNoResults` single paths).

`HardenedStreamer` change: the silent `runStreamer` recovery loop
(`client/ts/src/framer/streamer.ts:284-299`) reports each successful reopen to an epoch
callback instead of swallowing it. Lazy open is a wrapper in the framer family (NEW,
precedent: `HardenedStreamer` itself wrapping a `StreamOpener`).

## 2.4 - Data-structure responsibilities

- `cache.Store` per domain: single source of truth for one resource's records and
  tombstones. Entries map + parallel tombstones map; `delete` corpses, `set` clears.
  Never fetches; the domain client populates it.
- Engine: mechanism only. Zero domain knowledge, no schemas, no channel names of its
  own; domain clients hand it `StoreConfig`s. Owns liveness: one lazy streamer, epochs,
  reconciliation scheduling.
- Query lifecycle (shrunk `QueryCache`): dedup of in-flight retrieves and loading/error
  state per `hashQuery` key. Holds no long-lived data; stores do.
- Dispatch subsystem: undo/redo stacks keyed by store entry, session-local, dropped when
  a tombstone replaces the entry. Operates on plain stores; no special store kind
  exists.

## 2.5 - Testing

Two tiers, both existing patterns:

1. Pure-engine unit specs with a fake `StreamOpener` and `MockStreamer` (counting-
   opener pattern, `client/ts/src/framer/streamer.spec.ts:528+`). Exhaustive coverage of
   the state machines: tombstone transitions incl. delete-then-recreate ordering, epoch
   increment + diff reconciliation against scripted reconnects, optimistic
   write-through/rollback, writer-scope suppression, dispatch stacks and
   stack-drop-on-tombstone. This tier is the robust non-React suite the move exists to
   enable.
2. Live-core per-domain binding specs via `createTestClient` (`client/ts/src/testutil`,
   core at `localhost:9090`): real signal channels end to end, including the four new
   delete channels (delete via client A, assert client B's cache tombstones).

The existing `flux/base` specs move with their code and are adapted, not rewritten.

# 3 - Package: pluto flux (what remains)

## 3.1 - Surface

Factories only: `retrieve` (returning `useRetrieve`/`useGet`/`useEnsureRetrieved`/
`createSelector` per RFC §5.2), `update`, `dispatch`, `form`, `list`, plus
`Provider.tsx` and the aether provider. All are `useSyncExternalStore` bindings over the
domain clients' three read members (subscribe = `onChange`, snapshot = `getCached`,
fetch = `retrieve`); flux holds no state, mounts no listeners, and never sees a cache.
`mountListeners` leaves every factory config; its logic lives in the domain clients.
`result.ts` stays as the mutation `Result` shape, stripped of
`pendingResult`/`promise`/`name`.

## 3.2 - Store config relocation

The 25-entry `FLUX_STORE_CONFIG` (`pluto/src/Pluto.tsx:92`) and the 6-key worker subset
(`pluto/src/aether/pluto.ts:42`) dissolve: each domain's store config moves into its
`client/ts` domain client. Per-domain facts that must survive the move: user store has
no listeners; task mounts a third listener on `sy_task_cmd`; optimistic deletes touch
three stores (domain + relationships + resources via
`Ontology.filterRelationshipsThatHaveIDs`); panel/arc/schematic/lineplot/log/table lose
their undoable store kind and gain `undo(key)`/`redo(key)` domain methods backed by the
internal dispatch subsystem.

## 3.3 - Kill list

`pluto/src/flux/base/` in its entirety (post-move), the three barrels' base exports,
`useRetrieveStateful`/`useRetrieveEffect`/`useRetrieveObservable`/`Result`-returning
`useRetrieve` and internals (`retrieve.ts:199-394`), standalone `createSelector` store
plumbing, `beforeRetrieve`, `addStatusOnFailure`, form retrieve leg (`form.ts:187-214`),
`pendingResult`. The 11 synchronizer exports (ranger/status/ontology x4/view/device)
re-target from flux stores to the domain clients' `onChange` with signatures preserved.

## 3.4 - Testing

Live-core only (existing flux convention, no store-poking): suspense and boundary
behavior (`DisconnectedError`, `DeletedError`), derived selectors, forms, mutation
`Result`. Specs for moved machinery leave with the machinery.

# 4 - Console: Session Convergence and Persistence

## 4.1 - Synchronizer registry

Per-feature `SYNCHRONIZERS: Record<string, () => void>` hook consts (NEW, precedent:
`LINKS` consts + `Link.Registry`), spread-merged at one module-level site, mounted in
`Primary.tsx`'s `SideEffect` (today's 8 ad-hoc hook mounts at `Primary.tsx:27-37` fold
in). Contract: each hook covers live `onDelete` events and the epoch sweep (subscribing
via `client.cache.onEpoch`), dispatching through the same reducers. Never prune while
disconnected. Repair guards land in reducers per the panel `remove` template
(`console/src/session/panel/slice.ts:92-95`); missing today and added here: panel delete
synchronizer, cluster-remove clears selection, doc slices (schematic/line/table/arc/log)
prune on remote delete.

## 4.2 - Persist partitions

`console/src/persist` changes:

- Key scheme in the one existing KV (`V2_STORE_PATH`, engine opened once at
  `persist/store.ts:144`): `l0.<v>`, `l1.<clusterKey>.<v>`,
  `l2.<clusterKey>.<projectKey>.<v>`; per-partition version pointer generalizing
  `persistedStateKey` (`persist/state.ts:82`); 4-deep ring (`KEEP_HISTORY`) per
  partition. Slice-to-partition table from RFC §5.9. Delete the unused `historyLength?`
  config or wire it; do not leave it dangling.
- Middleware derives context synchronously via the pure selectors
  (`cluster/selectors.ts:31` `selectSelectedKey`, project `selectOptionalSelected`). On
  context-key change: flush outgoing partitions, load + migrate incoming, dispatch
  `persist/hydrate` carrying the partial state.
- Root reducer wrapper applies hydrate by replacing swapped slices wholesale; precedent
  for root-level state surgery: drift's `resetInitialState`
  (`drift/src/configureStore.ts:193`). Drift merges instead of replacing: keep live
  label/config/main-window, adopt stored project windows; sync middleware reopens them
  from the diff. Middleware order stays drift-sync -> Nav/Panel -> persist.
- `migrator` hook finally wired: loaded partitions pass through slice migrators before
  hydrate. One-time layout migration rewrites the current blob into `l0` plus the
  current context's `l1`/`l2`; idempotent, one-way.
- `window.location.reload` remains only in the `revertState`/`clearState` escape
  hatches.

## 4.3 - Tombstone UX

Mosaic tab boundary matches `DeletedError`, renders frozen corpse + banner + Close +
Restore (restore writes the corpse back through the domain client; key semantics are RFC
Open Question 1). Local deletes keep the existing `beforeUpdate` close dispatches.
Startup refs with no corpse: closed by the first epoch sweep.

## 4.4 - Testing

- Reducer repair guards: direct namespace specs (pure).
- Synchronizer hooks: `renderHook` + live core, dispatch-observing store built from the
  prod reducer.
- Persist: `kv.MockAsync` via `openKV` + manual middleware invocation for key scheme,
  ring, migration; hydrate-swap specs assert root wrapper + drift merge on a
  prod-reducer store.
- Playwright integration: project switch preserves and restores windows (the only
  cross-process flow).

# 5 - PR Packing

The five RFC phases land as three stacked PRs (rc <- PR1 <- PR2 <- PR3):

**PR 1 - cache substrate (phases 1+2).** Behavior-preserving end state; no user-visible
change. Go core delete channels (§1) as the opening commits, then the full `client/ts`
cache subsystem (§2) and the flux rebind + `flux/base` deletion + typed errors with
generic boundary fallbacks (§3.1/3.2). Phases 1 and 2 merge into one PR because phase 1
alone is dead code nothing in the app exercises; the rebind is what proves it. Still
green: every consumer keeps its current behavior. A first cut of this PR that moved the
cache while leaving the query lifecycle in flux was rejected in review (RFC Resolved
Decision 15) and reworked in place to the three-member domain surface; the rework
replaces, not stacks on, that cut.

**PR 2 - session robustness (phase 3, closes SY-4493).** §4 in full: tombstone tab UX
with Restore, synchronizer registry with the missing repairs (panel delete,
cluster-remove clears selection, doc-slice prunes), epoch sweep, startup
close-on-reconcile, L0/L1/L2 partitions with the reload-free hydrate swap, drift merge,
migrator wiring, one-time layout migration. All user-visible deletion and persistence
behavior isolated here for bisection.

**PR 3 - read-surface cutover (phases 4+5, the held 0047 scope).** Widest touch, lands
after the session program has soaked. Counts, census-verified: ~45
`Result`-`useRetrieve` sites + aliases, 13 stateful/effect/observable sites, ~60
selector defs (lineplot 20, panel 13, schematic 7, arc 7, log 7, table 5, ranger 1,
ethercat 1), access-`useGranted` internals (136 boolean call sites keep signatures), 16
form defs, 78 callback/utility sites onto `useGet`. Forms and callbacks stay separate
commits inside the PR so bisection still splits read mechanics from the fetch-behavior
change. Kill: observable substrate, standalone `createSelector`, `Result` read path,
dead exports. Zero coexistence after this lands.

46 console files reference Flux and are touched across PRs 1-3.
