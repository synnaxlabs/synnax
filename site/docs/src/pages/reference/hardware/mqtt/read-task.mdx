An MQTT read task subscribes to topics on a broker and records the values in their
payloads in channels. One task reads any number of topics, and it can also read
[Sparkplug B](/reference/hardware/mqtt/sparkplug) tags. Before you start,
[connect an MQTT broker](/reference/hardware/mqtt/connect-broker).

<Divider.Divider x />

## Message formats

An [interface control document (ICD)](/reference/hardware/icds) holds the messages that
a system sends, and the format of each one. For an MQTT topic, a message is the format
of a JSON payload: a list of fields. A field finds one value by a
[JSON pointer](https://datatracker.ietf.org/doc/html/rfc6901), such as `/temperature`,
and gives its type.

The task reads each topic as a message of an ICD. You choose the fields that the task
reads and the channel that records each one. The task does not read a field with no
channel.

- **Bare values** -> a field with an empty pointer reads the whole payload, such as
  `42.7`. A payload that is not JSON, such as `ON`, reads as a string.
- **All or nothing** -> the task writes all fields of a payload or none. It skips a
  payload that has no value for a field with no
  [default](/reference/hardware/icds/reference#defaults), or a value that the channel
  cannot hold.
- **Topics** -> a topic can be in a task once, and it cannot hold the wildcards `+` or
  `#`. Two topics cannot write to the same channel.
- **Shared formats** -> an ICD is not part of a task, so more than one task can read it.
  You cannot delete an ICD while a task reads it.
- **New topics** -> the message of a new topic goes into the ICD that most topics of the
  task read. A task with no topics creates an ICD named after the task.

When you upgrade the Core, it moves the fields of each read task from an earlier version
into a new ICD named after the task, with one message for each topic.

## Create an MQTT read task

<Client.Tabs exclude={["typescript"]}>
  <Fragment slot="console">

1. In the devices toolbar, right-click the broker and select **Create read task**. You
   can also run the "Create MQTT read task" command.
2. Click **Add data**. The dialog listens to the broker for 3 seconds and lists the
   topics that it saw.
3. Select a topic to see the last value and the type of each field, then select the
   values to read. For a topic that publishes rarely, click **Add a topic by name**.
4. Click **Add** _N_ **fields**. Each value becomes a field of the message format of its
   topic.
5. The fields of each topic are under it in the list. Select a field, and under
   **Field**, check its **Pointer** and **Type**.
6. Under **Channel**, set the **Data type** of the field's channel.
7. Click the dot of a field to turn it on or off. The task does not read a field that is
   crossed out.
8. To add a value that the dialog did not show, select the topic and click **Add
   field**.
9. Click <Icon.Play /> (**Start**).

The first topic makes an ICD named after the task. Each topic gets a message in it,
named after the topic. Click **Open in editor** to see the ICD in the ICD editor.

The Console creates a channel for each field that the task reads, and an index channel
for each message. It names them after the broker, the topic, and the field. To change
the name of a new channel, rename its field. After the task creates the channel, select
the field and type a new name in **Channel** to rename the channel.

A string, JSON, or bytes field reads into a
[virtual channel](/reference/channels#virtual-channels), which stores no data. So these
fields cannot share a message with number, boolean, or timestamp fields.

Python does not create channels. Create the channels and the ICD first.

```python
import synnax as sy
from synnax import mqtt

broker = client.devices.retrieve(name="Plant broker")
time = client.channels.create(
    name="line1_time", is_index=True, data_type=sy.DataType.TIMESTAMP
)
temperature = client.channels.create(
    name="line1_temperature", index=time.key, data_type=sy.DataType.FLOAT64
)
pressure = client.channels.create(
    name="line1_pressure", index=time.key, data_type=sy.DataType.FLOAT64
)

# The payload of plant/line1/sensors is {"temperature": 23.5, "pressure": 101.3}
temperature_field = sy.icd.FloatJSONField(
    name="temperature", pointer="/temperature"
)
pressure_field = sy.icd.FloatJSONField(name="pressure", pointer="/pressure")
sensors = sy.icd.Message(
    name="plant/line1/sensors",
    payload=sy.icd.JSONPayload(fields=[temperature_field, pressure_field]),
)
line1 = client.icds.create(name="Line 1", messages=[sensors])

task = mqtt.ReadTask(
    name="Line 1 sensors",
    device=broker.key,
    entries=[
        mqtt.PlainReadEntry(
            topic="plant/line1/sensors",
            icd=line1.key,
            messages=[
                sy.icd.ReadMessage(
                    message=sensors.key,
                    bindings=[
                        sy.icd.ReadBinding(
                            field=temperature_field.key,
                            channel=temperature.key,
                        ),
                        sy.icd.ReadBinding(
                            field=pressure_field.key, channel=pressure.key
                        ),
                    ],
                )
            ],
        )
    ],
)
client.tasks.configure(task)
task.start()
```

## Set a default or an enum mapping

The options of a field read values that its type alone cannot:

- **Default** -> the task writes the default when the payload has no value for the
  field. Scale and offset apply to the default as they do to a payload value. No value
  means that the pointer finds nothing. Except on a JSON channel, `null` is also no
  value, and so is `""` on a channel that is not a string or bytes channel. With no
  default, the task skips the payload.
- **Enum mapping** -> maps a text label in the payload, such as `ON`, to a value of the
  field's type, such as `1`.

Number, string, and boolean fields have options.

<Client.Tabs exclude={["typescript"]}>
  <Fragment slot="console">

1. Select the field.
2. To set a default, turn on **Optional**, then enter the **Default**.
3. To map a label, click **Add mapping** next to **Enum mapping**, then enter the
   **Label** and the **Value**.

  </Fragment>
  <Fragment slot="python">

```python
from x import payload

# The payload is {"state": "running", "level": 0.8}
state = sy.icd.UnsignedJSONField(
    name="state",
    pointer="/state",
    enum_values=[
        payload.UnsignedEntry(label="idle", value=payload.Unsigned(0)),
        payload.UnsignedEntry(label="running", value=payload.Unsigned(1)),
    ],
)
level = sy.icd.FloatJSONField(
    name="level", pointer="/level", default=payload.Float(0)
)
```

## Timestamps

Each message takes the timestamps of its samples from one of two sources:

- **Arrival time** -> the time at which the payload arrives at the Core. The default.
- **Payload value** -> a timestamp field of the message. The
  [type](/reference/hardware/icds/reference#types) of the field sets its format, and a
  field with a default cannot be the source. The value goes to the index channel of the
  message.

To read the time from the payload in the Console, set the **Type** of the field to a
timestamp type, such as **Timestamp (ms)**. Then, under **Timestamp**, set **Source** to
**Payload value** and select the **Field**. The list does not show the field, and
**Channel** under **Timestamp** names its index channel.

Timestamps in an index channel must increase. The task skips a payload whose timestamp
is not after the last one it wrote. A broker can send such a payload when it delivers a
message twice at quality of service 1.

In code, bind the timestamp field to the index channel, and put the key of the field in
`index` on the message:

```python
# The payload is {"value": 0.42, "ts": 1705312200000}
stamp = sy.icd.TimestampJSONField(
    name="ts", pointer="/ts", time_format="unix_ms"
)
value = sy.icd.FloatJSONField(name="value", pointer="/value")
sample = sy.icd.Message(
    name="sample", payload=sy.icd.JSONPayload(fields=[stamp, value])
)
read = sy.icd.ReadMessage(
    message=sample.key,
    index=stamp.key,
    bindings=[
        sy.icd.ReadBinding(field=stamp.key, channel=sample_time.key),
        sy.icd.ReadBinding(field=value.key, channel=sample_value.key),
    ],
)
```

## Read several messages from one topic

A device can publish more than one kind of payload on one topic, such as readings and
events, and mark each kind with a value such as `"type"`. Give each kind its own message
in the ICD, with a match rule that tells the task which message a payload is.

<Client.Tabs exclude={["typescript"]}>
  <Fragment slot="console">

1. Select the topic. Next to **Subscription**, click **Add message**. You can also
   right-click the topic and select **Add message**.
2. The topic now shows each of its messages, with the fields of each one under it.
   Select the new message.
3. Under **Documents**, set **Match** to the type of the value, then enter the
   **Pointer** and the **Value**. A new message tests the pointer of the other rules of
   the topic.
4. Next to **Message**, click **Add field** to add each field of the message.
5. Select the first message, and give it a match rule too, or leave it on **Any
   document** to read each payload that meets no rule.

To stop reading a message, right-click it and select **Remove**. The message stays in
the ICD. A topic always reads at least one message.

The Console creates an index channel for each message. From the second message on, a
channel name also holds the name of its message, such as
`broker_plant_line1_all_event_code`.

  </Fragment>
  <Fragment slot="python">

```python
# Readings are {"type": "reading", "temp": 21.4}.
# Events are {"type": "event", "code": 7}.
temp = sy.icd.FloatJSONField(name="temp", pointer="/temp")
reading = sy.icd.Message(
    name="reading",
    payload=sy.icd.JSONPayload(
        match=sy.icd.StringJSONMatch(pointer="/type", value="reading"),
        fields=[temp],
    ),
)
code = sy.icd.UnsignedJSONField(name="code", pointer="/code")
event = sy.icd.Message(
    name="event",
    payload=sy.icd.JSONPayload(
        match=sy.icd.StringJSONMatch(pointer="/type", value="event"),
        fields=[code],
    ),
)
line1 = client.icds.create(name="Line 1", messages=[reading, event])

# temperature and event_code are on different index channels.
entry = mqtt.PlainReadEntry(
    topic="plant/line1/all",
    icd=line1.key,
    messages=[
        sy.icd.ReadMessage(
            message=reading.key,
            bindings=[sy.icd.ReadBinding(field=temp.key, channel=temperature.key)],
        ),
        sy.icd.ReadMessage(
            message=event.key,
            bindings=[sy.icd.ReadBinding(field=code.key, channel=event_code.key)],
        ),
    ],
)
```

<Rule.List>
<Rule.Item title="A payload is read as the message whose rule it meets">

A match rule names a pointer and a string, boolean, or number value. A payload meets the
rule when its value at the pointer is equal to the value of the rule.

</Rule.Item>
<Rule.Item title="Each rule of a topic tests the same pointer">

The messages of one topic cannot test different pointers.

</Rule.Item>
<Rule.Item title="Two rules cannot match the same value">

The numbers `1` and `1.0` are the same value.

</Rule.Item>
<Rule.Item title="One message can have no rule">

It reads each payload that meets no rule.

</Rule.Item>
<Rule.Item title="A payload that matches no message is skipped">

The task warns with `the payload matches no message`.

</Rule.Item>
<Rule.Item title="Each message writes to its own channels">

Two messages cannot write to the same channel, an index channel included.

</Rule.Item>
</Rule.List>

## Read a message format that you defined first

You can define the messages of a device in the ICD editor first, then read them in a
task.

1. Click **Add data**, then **Add a topic by name**.
2. Enter the **Topic**.
3. Set **Message format** to the message. The list shows each JSON message, with the
   name of its ICD.

The task reads each field of the message. A string field among number fields stays
unread, as they cannot share an index channel. A field keeps the channel that the topic
wrote for the same pointer when the channel's data type fits the field, so plots and
ranges keep their data. Otherwise, the field gets a new channel when you deploy. When
the message has one timestamp field with no default, the topic reads its time from that
field. The message that the topic read before stays in its ICD. **Message format** shows
only on a topic that reads one message.

In code, set the `icd` of the topic and the `message` of its `ReadMessage`.

## Edit the message format of a running task

The message format belongs to the ICD, not to the task. An edit to it, in the task tab
or in the ICD editor, saves at once. A running task keeps the format that it started
with, and its task tab shows **Redeploy**. To read with the new format,
[redeploy the task](/reference/hardware/start-and-stop-tasks#apply-edits-to-a-running-task).
In Python, call `task.start()` again.

An edit can give a field a type that its channel cannot hold. On **Redeploy** in the
task tab, the Console gives the field a new channel. In Python, `client.tasks.configure`
raises a validation error, and `task.start()` fails with **Failed to configure task**.
See [troubleshooting](#troubleshooting).

## Retained messages

When the task subscribes, the broker sends the retained message of each topic, if it has
one. The task records it like any other message, but skips it with no warning when its
timestamp is not after the last one written. Turn on **Ignore retained** to always skip
it.

## Task options

| Setting                                           | Default | Notes                                                     |
| ------------------------------------------------- | ------- | --------------------------------------------------------- |
| Data saving <small>`data_saving_disabled`</small> | On      | See [data saving](/reference/hardware/tasks#data-saving). |
| Auto start <small>`auto_start`</small>            | Off     | Starts the task each time the Core starts.                |

The task has no sample rate. It writes each payload when it arrives.

## Topic reference

A topic has these settings:

| Setting                                           | Default      | Notes                                                     |
| ------------------------------------------------- | ------------ | --------------------------------------------------------- |
| Topic <small>`topic`</small>                      |              | The topic to subscribe to, such as `plant/line1/sensors`. |
| Quality of service <small>`qos`</small>           | At most once | At most once (0), at least once (1), or exactly once (2). |
| Ignore retained <small>`retained_ignored`</small> | Off          | Skips the retained message of the topic.                  |
| Source <small>`index`</small>                     | Arrival time | The key of the timestamp field, on each `ReadMessage`.    |
| Message format <small>`icd`</small>               |              | The key of the ICD that holds the messages of the topic.  |

In code, a topic is `PlainReadEntry`, of type `"plain"`. The `qos` values are
`"at_most_once"`, `"at_least_once"`, and `"exactly_once"`. Its `messages` are each an
`sy.icd.ReadMessage`, with the key of the `message`, its `index`, and its `bindings`. An
`sy.icd.ReadBinding` gives the key of a `field` and the `channel` that records it.

The [ICD reference](/reference/hardware/icds/reference) lists the properties of a
message and its fields, and the data types that each field type can write to.

## Troubleshooting

<Problem.List>

<Problem.Item message={"Skipped ... of ... messages"}>
<Problem.Cause>

The task read some messages that it cannot record. The description gives the topic and
the reason for the last one, such as `field temp: no value at /temp`, a payload that
matches no message, or a timestamp that is not after the last one written. The warning
clears 5 seconds after the last skip.

</Problem.Cause>
<Problem.Fix>

Check the pointers and types of the message format against a payload from the topic.
Pointers start with `/` and are case sensitive.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"messages arrive faster than the task can write them, and the oldest are dropped"}>
<Problem.Cause>

The task holds up to 4096 messages that wait to be written. More messages arrived, so
the task dropped the oldest ones.

</Problem.Cause>
<Problem.Fix>

Lower the rate at which the devices publish to the topics of the task.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"the broker refused the subscription to ..."}>
<Problem.Cause>

The broker does not let the user subscribe to the topic, for example because of an
access rule. At start, the task does not start. After the connection returns, the task
keeps running and shows this warning.

</Problem.Cause>
<Problem.Fix>

Give the user access to the topic in the broker, then start the task again.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"broker is not connected"}>
<Problem.Cause>

The connection to the broker is down. The Core connects again on its own, and the
warning clears when the connection returns.

</Problem.Cause>
</Problem.Item>

<Problem.Item symptom="The task reads with the old message format">
<Problem.Cause>

A running task keeps the message format that it started with. An edit to the format
saves at once, but the task uses it only after a redeploy.

</Problem.Cause>
<Problem.Fix>

Click **Redeploy** in the task tab. In Python, call `task.start()` again.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={["field ... of kind ... cannot read into channel ... of data type ...", "cannot write ... values to ... channels", "a scaled field requires a float channel, not ..."]}>
<Problem.Cause>

The type of a field does not fit the data type of its channel. A field with a **Scale**
or an **Offset** needs a float channel.

</Problem.Cause>
<Problem.Fix>

Change the **Type** of the field, or read it into a channel of a data type that fits.
See [types](/reference/hardware/icds/reference#types). After an edit of the type,
**Redeploy** in the Console gives the field a new channel.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={["the index field ... must be a timestamp field", "the index field ... cannot take a default", "the index field ... must write to an index channel", "only the index field can write to index channel ..."]}>
<Problem.Cause>

The `index` of a message names a field that cannot give timestamps, or a field other
than the index writes to an index channel. An index field cannot have a default, because
each sample needs the time from its own payload.

</Problem.Cause>
<Problem.Fix>

Set `index` to a timestamp field with no default, and bind it to the index channel. Bind
each other field to a data channel. To remove a default in the Console, open the field's
**Options** in the ICD editor and turn off **Optional**.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={["The task reads no fields of ...", "topic ... reads no messages", "message ... binds no fields"]}>
<Problem.Cause>

A topic, or a message of a topic, reads no field.

</Problem.Cause>
<Problem.Fix>

Turn on a field of the topic or the message. Or disable the topic, or remove the
message.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={["messages ... and ... both have no match rule", "messages ... and ... match at different pointers ... and ...", "messages ... and ... match the same value ..."]}>
<Problem.Cause>

The match rules of a topic cannot tell its payloads apart. Only one message of a topic
can have no rule, each rule must test the same pointer, and no two rules can match the
same value.

</Problem.Cause>
<Problem.Fix>

Select each message of the topic and change its **Match**. See
[read several messages from one topic](#read-several-messages-from-one-topic).

</Problem.Fix>
</Problem.Item>

<Problem.Item message={["entries: topic ... appears more than once", "entries: ... and ... write to the same channel ...", "channel ... is also written by ..."]}>
<Problem.Cause>

Two entries read the same topic, or two fields write to the same channel.

</Problem.Cause>
<Problem.Fix>

Read each topic once, and give each field its own channel. Give each message of a topic
its own index channel.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"cannot delete icd ... because task ... uses it"}>
<Problem.Cause>

A read task reads the ICD, also from a disabled topic.

</Problem.Cause>
<Problem.Fix>

Delete the task, or remove its topics that read the ICD, then delete the ICD.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"entries: the task has no enabled entries"}>
<Problem.Cause>

The task has no entries, or each entry is disabled.

</Problem.Cause>
<Problem.Fix>

Add an entry, or enable one.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"device: a broker is required"}>
<Problem.Cause>

The task has no broker. In code, `device` is empty.

</Problem.Cause>
<Problem.Fix>

Set `device` to the key of the broker.

</Problem.Fix>
</Problem.Item>

</Problem.List>

For problems with the connection, see
