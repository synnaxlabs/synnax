An OPC UA write task writes a value to a node each time you write a value to a command
channel. For example, a valve on a schematic can set a PLC setpoint. A channel can also
[call a method](#call-a-method) of the server. If you write several values at once, the
task writes only the last one. The task writes single values, not arrays.

The task has no state channels. To see the value on the server, read the node back with
an [OPC UA read task](/reference/hardware/opc-ua/read-task). Before you start, you need
a [connected OPC UA server](/reference/hardware/opc-ua/connect-server).

## Create an OPC UA write task

When you create command channels with a client library, give each one its own index
channel. A writer that holds several commands on one index must write all of them in
every frame.

<Client.Tabs>
  <Fragment slot="console">

1. In the devices toolbar, right-click the server and select **Create write task**.
2. In the **Browser**, expand the folders of the server.
3. Drag the variables to write into **Channels**.
4. Click <Icon.Play /> (**Start**).

The Console creates a command channel for each node, named `<node>_cmd`, and its index
`<node>_cmd_time`. To choose another name, right-click the channel and select **Rename**
before you start.

To add many nodes at once, drag a folder into **Channels**, or import a CSV file. See
[find nodes](/reference/hardware/opc-ua/read-task#find-nodes). A write task CSV has no
`index` column, and the Console skips rows with a `field`.

<Video id="hardware/opc-ua/write-task" />

  </Fragment>
  <Fragment slot="python">

Python does not create channels. Create the command channel and its index first.

```python
import synnax as sy
from synnax import opcua

server = client.devices.retrieve(name="Line 1 PLC")
cmd_time = client.channels.create(
    name="pump_setpoint_cmd_time", is_index=True, data_type=sy.DataType.TIMESTAMP
)
cmd = client.channels.create(
    name="pump_setpoint_cmd", index=cmd_time.key, data_type=sy.DataType.FLOAT64
)

task = opcua.WriteTask(
    name="Line 1 PLC write",
    device=server.key,
    channels=[
        opcua.NodeWriteChannel(cmd_channel=cmd.key, node_id="NS=2;S=Pump1.Setpoint")
    ],
)
client.tasks.configure(task)
task.start()
```

  </Fragment>
  <Fragment slot="typescript">

TypeScript does not create channels. Create the command channel and its index first.

```typescript
import { opcua } from "@synnaxlabs/client";

const [server] = await client.devices.retrieve({ names: ["Line 1 PLC"] });
const cmdTime = await client.channels.create({
  name: "pump_setpoint_cmd_time",
  isIndex: true,
  dataType: "timestamp",
});
const cmd = await client.channels.create({
  name: "pump_setpoint_cmd",
  index: cmdTime.key,
  dataType: "float64",
});

const task = await client.tasks.create({
  name: "Line 1 PLC write",
  rack: server.rack,
  type: "opc_write",
  config: opcua.writeConfigZ.parse({
    device: server.key,
    channels: [{ type: "node", cmdChannel: cmd.key, nodeId: "NS=2;S=Pump1.Setpoint" }],
  }),
});
await task.start();
```

  </Fragment>
</Client.Tabs>

The OPC UA write task has one option, **Auto start** (`auto_start`), which starts the
task each time the Driver starts. For node IDs, see
[node IDs](/reference/hardware/opc-ua/read-task#node-ids). When a frame has more
commands than the server accepts in one request, the Driver splits the write into
smaller requests.

## Call a method

A method channel calls a method of the server each time its command channel gets a
value. For example, a button on a schematic can call `Start` on a pump.

<Client.Tabs>
  <Fragment slot="console">

1. In the **Browser**, expand the object that holds the method.
2. Drag the method <Icon.Function /> into **Channels**. The Console reads the input
   arguments of the method.
3. Select the channel. For each argument, type a value, or turn on **Command** to give
   the argument the value of the command.
4. Click <Icon.Play /> (**Start**).

The first argument takes the command by default, and the command channel takes the type
of that argument. When no argument takes the command, each command calls the method,
whatever its value, and the command channel is `uint8`.

To call one method with different arguments, drag it again. Each channel gets its own
command channel, named `<method>_cmd`, then `<method>_cmd_2`, and so on. A CSV file
holds no method channels.

  </Fragment>
  <Fragment slot="python">

```python
cmd_time = client.channels.create(
    name="pump_speed_cmd_time", is_index=True, data_type=sy.DataType.TIMESTAMP
)
cmd = client.channels.create(
    name="pump_speed_cmd", index=cmd_time.key, data_type=sy.DataType.FLOAT64
)

task = opcua.WriteTask(
    name="Line 1 pump",
    device=server.key,
    channels=[
        opcua.MethodWriteChannel(
            cmd_channel=cmd.key,
            node_id="NS=2;S=Pump1.Configure",
            object_id="NS=2;S=Pump1",
            arguments=[
                opcua.ValueMethodArgument(value="auto"),
                opcua.CommandMethodArgument(),
            ],
        )
    ],
)
client.tasks.configure(task)
task.start()
```

  </Fragment>
  <Fragment slot="typescript">

```typescript
const task = await client.tasks.create({
  name: "Line 1 pump",
  rack: server.rack,
  type: "opc_write",
  config: opcua.writeConfigZ.parse({
    device: server.key,
    channels: [
      {
        cmdChannel: cmd.key,
        type: "method",
        nodeId: "NS=2;S=Pump1.Configure",
        objectId: "NS=2;S=Pump1",
        arguments: [{ source: "value", value: "auto" }, { source: "command" }],
      },
    ],
  }),
});
await task.start();
```

  </Fragment>
</Client.Tabs>

The Driver converts each argument to the type that the method declares, with the rules
in [data types](#data-types). A value that you type is text, so `3.5` fits a Double
argument and `true` fits a Boolean argument. When the server rejects a call, the task
shows ["Failed to write commands"](#troubleshooting) with the reason.

When the connection drops during a call, the Driver does not call the method again,
because the server might have run it. A write to a node is safe to repeat, so the Driver
writes it again. Use a method for an action that must run only once.

## Channel reference

The table shows the Console label of each setting, with its Python field under it.

| Setting                              | Default   | Notes                                                                                                             |
| ------------------------------------ | --------- | ----------------------------------------------------------------------------------------------------------------- |
| Channel name <small>`name`</small>   | Empty     | The name of the command channel that the Console creates.                                                         |
| <small>`cmd_channel`</small>         |           | The key of the command channel.                                                                                   |
| <small>`type`</small>                |           | `node` writes the node. `method` calls the method. In Python, `NodeWriteChannel` or `MethodWriteChannel` sets it. |
| Node ID <small>`node_id`</small>     |           | See [node IDs](/reference/hardware/opc-ua/read-task#node-ids).                                                    |
| Object <small>`object_id`</small>    | Empty     | For a method, the node ID of the object that holds it.                                                            |
| <small>`arguments`</small>           | Empty     | For a method, its input arguments, in order.                                                                      |
| Node name <small>`node_name`</small> | Empty     | The browse name. For display only.                                                                                |
| <small>`data_type`</small>           | `float32` | For a node, the data type of the command channel that the Console creates.                                        |
| Enabled <small>`disabled`</small>    | Off       | A disabled channel is not written.                                                                                |

Each argument has these settings:

| Setting                         | Default | Notes                                                                                                                                                       |
| ------------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Command <small>`source`</small> |         | `value` gives the argument a fixed value. `command` gives it the value of the command. In Python, `ValueMethodArgument` or `CommandMethodArgument` sets it. |
| <small>`value`</small>          | Empty   | The value of the argument when `source` is `value`, as text. The Console shows it under the name of the argument.                                           |
| <small>`name`</small>           | Empty   | The name that the method declares. For display only.                                                                                                        |
| <small>`data_type`</small>      | Empty   | The Synnax type of the argument. The Console gives it to the command channel.                                                                               |

### Data types

The Driver reads the type of each node when it connects, and converts each command to
that type. For example, a `float64` channel can write `3` to an Int16 node, or `1` to a
Boolean node.

| OPC UA type        | Accepts                                                    |
| ------------------ | ---------------------------------------------------------- |
| Boolean            | `0`, `1`, or the text `true` or `false`                    |
| An integer type    | A whole number in the range of the type, or the text of it |
| Float, Double      | A number, or the text of one                               |
| String             | Any value except a timestamp, written as text              |
| DateTime           | A `timestamp`                                              |
| Guid               | A `uuid`, or the text of a GUID                            |
| ByteString         | A `bytes` or a `string`                                    |
| An enumeration     | A whole number in the range of `int32`                     |
| BaseDataType (any) | Any value, with the type in the table below                |

The Driver does not send a command that does not fit the node, such as `300` for a Byte
node or `1.5` for an Int16 node. The task shows
["Failed to write commands"](#troubleshooting) and writes the other channels.

When the server does not give the type of a node, the Driver writes the value with the
OPC UA type of the command channel:

| Synnax data type | OPC UA type |
| ---------------- | ----------- |
| `boolean`        | Boolean     |
| `int8`           | SByte       |
| `uint8`          | Byte        |
| `int16`          | Int16       |
| `uint16`         | UInt16      |
| `int32`          | Int32       |
| `uint32`         | UInt32      |
| `int64`          | Int64       |
| `uint64`         | UInt64      |
| `float32`        | Float       |
| `float64`        | Double      |
| `string`         | String      |
| `timestamp`      | DateTime    |
| `uuid`           | Guid        |
| `bytes`          | ByteString  |

A write task cannot write to a field of a structure node.

## Troubleshooting

<Problem.List>

<Problem.Item message={"... returned BadTypeMismatch. The value supplied for the attribute is not of the same type as the attribute's value."}>
<Problem.Cause>

The server did not give the type of the node, so the Driver wrote the type of the
command channel, and the type does not match the node.

</Problem.Cause>
<Problem.Fix>

Use the data type from the [table](#data-types). For example, a Double node needs a
`float64` channel.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"... returned BadNodeIdUnknown. The node id refers to a node that does not exist in the server address space."}>
<Problem.Cause>

The server has no node with that ID.

</Problem.Cause>
<Problem.Fix>

Drag the node from the **Browser** again.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"... the server has no namespace ..."}>
<Problem.Cause>

The server has no namespace with the URI in the node ID of the channel. The server can
add the namespace later, for example when a PLC loads its program.

</Problem.Cause>
<Problem.Fix>

Check that the server loaded its program, or drag the node from the **Browser** again.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"... returned BadNotWritable. The access level does not allow writing to the Node."}>
<Problem.Cause>

The node is read only on the server, or the user of the connection cannot write to it.

</Problem.Cause>
<Problem.Fix>

Make the node writable on the server, or connect with a user that can write to it.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"Invalid NodeId format"}>
<Problem.Cause>

The node ID is not in a form that the Driver accepts.

</Problem.Cause>
<Problem.Fix>

Write the node ID in one of the forms in
[node IDs](/reference/hardware/opc-ua/read-task#node-ids).

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"... the method takes 2 arguments, but the channel gives 1 argument."}>
<Problem.Cause>

The method on the server has a different number of arguments than the channel. The
method changed after you added the channel.

</Problem.Cause>
<Problem.Fix>

Remove the channel and drag the method from the **Browser** again.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"... lost the connection during the call, so the method might not have run."}>
<Problem.Cause>

The connection dropped after the Driver sent the call. The Driver cannot know if the
server ran the method, so it does not call it again.

</Problem.Cause>
<Problem.Fix>

Check the state of the equipment before you send the command again.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"Failed to write commands"}>
<Problem.Cause>

The task could not write a command. The description names each channel and the reason.
The task writes the other channels of the command and keeps running. When the connection
is lost, the Driver connects again once and repeats the write, so a value that the
server already got can arrive twice. If that fails, the task drops the command. It does
not keep commands for later, because a late command could move hardware at the wrong
time.

</Problem.Cause>
<Problem.Fix>

Fix the cause in the description. For a lost connection, check the
[server connection](/reference/hardware/opc-ua/connect-server#troubleshooting). The next
command connects again.

</Problem.Fix>
</Problem.Item>

</Problem.List>

For other problems, see [Troubleshoot hardware](/reference/hardware/troubleshooting).
