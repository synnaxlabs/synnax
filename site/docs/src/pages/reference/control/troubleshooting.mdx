## Schematics

### The schematic has no control button

<Problem.Body>
<Problem.Cause>

Your role is Viewer. A viewer cannot control hardware.

</Problem.Cause>
<Problem.Fix>

Ask an administrator for the Operator role or higher.

</Problem.Fix>
</Problem.Body>

### A click on a valve does nothing

<Problem.Body>
<Problem.Cause>

One of these:

- Editing is on, so the click selects the symbol.
- The schematic does not have control. Another writer with a higher authority holds the
  channel, or one with the same authority got it first.
- The command channel has no write task, or the symbol has no state channel, so the
  valve never shows as open.

</Problem.Cause>
<Problem.Fix>

1. Turn off editing, and take control.
2. Look at the [control legend](/reference/control/manual#control-legend) to see which
   writer controls the channel. To take over, see
   [take absolute control](/reference/control/manual#take-absolute-control-of-one-channel).
3. Check the channels of the symbol. See
   [what each symbol writes](/reference/control/manual#what-each-symbol-writes).

</Problem.Fix>
</Problem.Body>

### `No symbols control any channels.`

<Problem.Body>
<Problem.Cause>

No symbol on the schematic has a command channel. The notification shows "Failed to
acquire control", with this text in the description.

</Problem.Cause>
<Problem.Fix>

Turn on editing, and set a channel in the **Control** tab of each symbol.

</Problem.Fix>
</Problem.Body>

### `Some symbols use channels that no longer exist.`

<Problem.Body>
<Problem.Cause>

A symbol uses a command channel that was deleted. The notification shows "Skipped
deleted channels", with this text and the missing channels in the description. The
schematic takes control of the other channels.

</Problem.Cause>
<Problem.Fix>

Turn on editing, and set a channel that exists in the **Control** tab of each symbol
that used a deleted channel.

</Problem.Fix>
</Problem.Body>

### The schematic has no Control tab

<Problem.Body>
<Problem.Cause>

Your role is Operator. Operators cannot edit schematics, so they write at authority 1.

</Problem.Cause>
<Problem.Fix>

Ask an administrator for the Engineer role.

</Problem.Fix>
</Problem.Body>

## Authority

### Synnax drops commands with no error

<Problem.Body>
<Problem.Cause>

Another writer controls the channel. Synnax drops writes from a writer that does not
have control. It reports an error only when the writer opens, and only if the writer
asks for it.

</Problem.Cause>
<Problem.Fix>

[See which writer controls the channel](/reference/control/authority#see-which-writer-controls-a-channel).
Then lower its authority, or raise yours above it. To find dropped commits in code,
commit with `commit_result` in Python or `commitResult` in TypeScript, and check
`authorized`. See [set authority](/reference/control/authority#set-authority).

</Problem.Fix>
</Problem.Body>

### `<writer> has no control authority - it is currently held by <writer>`

<Problem.Body>
<Problem.Cause>

The writer asked for an error when it opens without control, and another writer holds
the channel.

</Problem.Cause>
<Problem.Fix>

Stop the other writer, or open yours with a higher authority.

</Problem.Fix>
</Problem.Body>

### `cannot access time range <range> because writer <writer> holds it`

<Problem.Body>
<Problem.Cause>

A writer in `persist` mode, such as the Python or TypeScript `client.write` method,
writes to a time range that another writer holds. A read task holds its channels while
it runs. A `persist` writer never takes control, at any authority.

</Problem.Cause>
<Problem.Fix>

Write to a time range before the other writer started, or stop the other writer first.
See [how authority works](/reference/control/authority#how-authority-works).

</Problem.Fix>
</Problem.Body>

### Authority 255 does not take control

<Problem.Body>
<Problem.Cause>

On a channel with an index, a tie goes to the writer that got control first. A writer at
255 does not take control from another writer at 255. On a virtual channel, every writer
at the controlling authority or above it writes.

</Problem.Cause>
<Problem.Fix>

Give automations a lower authority, such as 100, so that operators can take over at 255.
See [control authority](/reference/control/authority).

</Problem.Fix>
</Problem.Body>

### An operator takes a channel from an automation, but commands do nothing

<Problem.Body>
<Problem.Cause>

The automation sets a per-channel authority with no default, such as
`authority (vent_vlv_cmd 100)`. Its index channels stay at 255. The schematic also
writes the index channel and loses it, so Synnax drops its writes to every channel on
that index.

</Problem.Cause>
<Problem.Fix>

Give the authority line a default: `authority (100 vent_vlv_cmd 200)`.

</Problem.Fix>
</Problem.Body>

## Arc automations

### The stage indicator shows a running sequence, but the valves do not move

<Problem.Body>
<Problem.Cause>

The automation has a lower authority than the schematic. A click on any button takes
control of every actuated symbol on the schematic, valves included. Synnax then drops
the commands from the sequence.

</Problem.Cause>
<Problem.Fix>

Keep the automation authority above the schematic authority, or put the start button on
a separate schematic. See
[start a sequence from a schematic](/reference/control/arc/start-from-schematic#start-the-test).

</Problem.Fix>
</Problem.Body>

### The abort stage runs at the end of a normal run

<Problem.Body>
<Problem.Cause>

A write, a wait, or a gate step moves on to the next step in the code, also when the
next step is a named stage. An abort stage right after such a step runs when the steps
before it finish.

</Problem.Cause>
<Problem.Fix>

Put the abort stage where no step leads into it, such as after a stage that only leaves
by name. See
[steps of a sequence](/reference/control/arc/execution-model#steps-of-a-sequence).

</Problem.Fix>
</Problem.Body>

### The sequence runs once and never starts again

<Problem.Body>
<Problem.Cause>

The sequence ends in a stage, so it never stops. A start command to a running sequence
does nothing.

</Problem.Cause>
<Problem.Fix>

End the sequence with a write, a wait, or a gate, such as `0 -> vent_vlv_cmd`. See
[when a sequence stops](/reference/control/arc/execution-model#when-a-sequence-stops).

</Problem.Fix>
</Problem.Body>

### A transition does not fire when the stage starts

<Problem.Body>
<Problem.Cause>

A stage reacts only to values that arrive after it starts. A condition such as
`tank_pt > 300` waits for the next `tank_pt` value, even when the last value was 400.

</Problem.Cause>
<Problem.Fix>

No fix is necessary when the sensor streams. See
[entering a stage](/reference/control/arc/execution-model#entering-a-stage).

</Problem.Fix>
</Problem.Body>

### `The <type> node failed: WASM execution failed in node <key> at sample <i>/<n>: ...`

<Problem.Body>
<Problem.Cause>

A runtime error, such as an index out of bounds. On a Driver, the status shows "Failed
to run Arc program" with this text in the description, and the automation stops. On the
Core, the status shows "Node failed", and the Core drops the cycle and keeps running.

</Problem.Cause>
<Problem.Fix>

Fix the code. See
[errors while it runs](/reference/control/arc/execution-model#errors-while-it-runs).

</Problem.Fix>
</Problem.Body>

### The automation list shows Stopped for a running automation

<Problem.Body>
<Problem.Cause>

A known bug. The list shows **Stopped** when a running automation has a warning.

</Problem.Cause>
<Problem.Fix>

Open the automation to see its real status and the warning.

</Problem.Fix>
</Problem.Body>

### A Driver is not in the list

<Problem.Body>
<Problem.Cause>

The list shows only Drivers with the `arc` integration turned on. All Drivers have it by
default, but a Driver configuration can remove it.

</Problem.Cause>
<Problem.Fix>

Add `arc` to the integrations of the Driver. **Deploy** stays off until you choose a
Driver.

</Problem.Fix>
</Problem.Body>

### `undefined symbol: <name>`

<Problem.Body>
<Problem.Cause>

No channel, variable, or function has that name. Channel names are case sensitive.

</Problem.Cause>
<Problem.Fix>

Create the channel, or correct the name.

</Problem.Fix>
</Problem.Body>

## Python

### Controller commands do nothing and raise no error

<Problem.Body>
<Problem.Cause>

Another writer controls the channel. A `Controller` does not ask for an error, so Synnax
drops its writes.

</Problem.Cause>
<Problem.Fix>

See [Synnax drops commands with no error](#synnax-drops-commands-with-no-error).

</Problem.Fix>
</Problem.Body>

### `authorities: authorities must be a single authority or a slice of authorities with the same length as keys`

<Problem.Body>
<Problem.Cause>

`write_authorities` has more than one value. The controller adds the index channels to
its write channels, so the counts do not match.

</Problem.Cause>
<Problem.Fix>

Give one authority for all channels. Change it per channel with `set_authority` after
the controller opens.

</Problem.Fix>
</Problem.Body>

### `Channel ... not found in controller state`

<Problem.Body>
<Problem.Cause>

The code reads a channel that is not in the `read` list of the controller, or that has
no value yet.

</Problem.Cause>
<Problem.Fix>

Add the channel to `read`, or wait for its first value with `wait_until_defined`.

</Problem.Fix>
</Problem.Body>

### The sequence goes on before the condition is true

<Problem.Body>
<Problem.Cause>

`wait_until` returns `False` at the timeout. It raises no error. It also returns at once
if a value from before the call satisfies the condition.

</Problem.Cause>
<Problem.Fix>

Check the return value, and abort when it is `False`. To wait for a new value, wait for
the state to leave the old value first. See
[Wait for a new value](/reference/control/python/write-sequences#wait-for-a-new-value).

</Problem.Fix>
</Problem.Body>
