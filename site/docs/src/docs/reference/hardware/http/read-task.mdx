An HTTP read task polls a web API at a fixed rate and records values from each JSON
response in channels. Before you start,
[connect an HTTP server](/reference/hardware/http/connect-server).

<Divider.Divider x />

## Message formats

An [interface control document (ICD)](/reference/hardware/icds) holds the messages that
a system sends, and the format of each one. For an HTTP endpoint, a message is the
format of a JSON response: a list of fields. A field finds one value by a
[JSON pointer](https://datatracker.ietf.org/doc/html/rfc6901), such as `/temperature`,
and gives its type.

The task reads each response of an endpoint as a message of an ICD. You choose the
fields that the task reads and the channel that records each one. The task does not read
a field with no channel.

- **Strings** -> a numeric field reads a number in a string, such as `"23.5"`. An
  [enum mapping](#set-a-default-or-an-enum-mapping) maps a text label to a value.
- **Several messages** -> an endpoint can read more than one message. Each message has a
  match rule under **Responses** that selects the responses it reads.
- **Shared formats** -> an ICD is not part of a task, so more than one task can read it.
  You cannot delete an ICD while a task reads it.
- **New endpoints** -> the message of a new endpoint goes into the ICD that most
  endpoints of the task read. A task with no endpoints creates an ICD named after the
  task.

The **Source** under **Timestamp** of a message sets its timestamps:

- **Poll time** -> the time halfway through the request.
- **Payload value** -> the value of a timestamp **Field** of the message, in the format
  of that field: ISO 8601, or Unix time in seconds, milliseconds, microseconds, or
  nanoseconds. A field with a default cannot give the timestamps.

When you upgrade the Core, it moves the fields of each read task from an earlier version
into a new ICD named after the task, with one message for each endpoint.

## Create an HTTP read task

<Client.Tabs>
  <Fragment slot="console">

1. In the devices toolbar, right-click the server and select **Create read task**.
2. Set **Rate**, the number of requests per second to each endpoint.
3. Click **Add endpoint**, then set **Method** and **Path**, such as `/api/data`, under
   **Request**.
4. Click **Add field**. Select the field, and under **Field**, set its **Pointer** and
   **Type**.
5. Under **Channel**, set the **Data type** of the field's channel.
6. Select the endpoint, and under **Timestamp**, set the **Source**.
7. Click <Icon.Play /> (**Start**).

The Console creates a channel for each field that the task reads, and an index channel
for each message. It names them after the server, the path, and the field. To change the
name of a new channel, rename its field.

  <Fragment slot="python">

Python does not create channels. Create the channels and the ICD first.

```python
import synnax as sy
from synnax import http

server = client.devices.retrieve(name="Weather station")
time = client.channels.create(
    name="weather_time", is_index=True, data_type=sy.DataType.TIMESTAMP
)
temperature = client.channels.create(
    name="weather_temperature", index=time.key, data_type=sy.DataType.FLOAT64
)

# The response of GET /api/data is {"temperature": 23.5}
temperature_field = sy.icd.FloatJSONField(
    name="temperature", pointer="/temperature"
)
data = sy.icd.Message(
    name="GET /api/data",
    payload=sy.icd.JSONPayload(fields=[temperature_field]),
)
station = client.icds.create(name="Weather station", messages=[data])

task = http.ReadTask(
    name="Weather station read",
    device=server.key,
    rate=1,
    endpoints=[
        http.ReadEndpoint(
            method="GET",
            path="/api/data",
            icd=station.key,
            messages=[
                sy.icd.ReadMessage(
                    message=data.key,
                    bindings=[
                        sy.icd.ReadBinding(
                            field=temperature_field.key, channel=temperature.key
                        )
                    ],
                )
            ],
        )
    ],
)
client.tasks.configure(task)
task.start()
```

TypeScript does not create channels. Create the channels and the ICD first.

```typescript
import { http, icd } from "@synnaxlabs/client";

const [server] = await client.devices.retrieve({
  where: { name: { eq: "Weather station" } },
});
const time = await client.channels.create({
  name: "weather_time",
  isIndex: true,
  dataType: "timestamp",
});
const temperature = await client.channels.create({
  name: "weather_temperature",
  index: time.key,
  dataType: "float64",
});

// The response of GET /api/data is {"temperature": 23.5}
const temperatureField = icd.floatJSONFieldZ.parse({
  type: "float",
  name: "temperature",
  pointer: "/temperature",
});
const data = icd.messageZ.parse({
  name: "GET /api/data",
  payload: { format: "json", fields: [temperatureField] },
});
const station = await client.icds.create({ name: "Weather station", messages: [data] });

const task = await client.tasks.create({
  name: "Weather station read",
  rack: server.rack,
  type: "http_read",
  config: http.readConfigZ.parse({
    device: server.key,
    rate: 1,
    endpoints: [
      {
        method: "GET",
        path: "/api/data",
        icd: station.key,
        messages: [
          {
            message: data.key,
            bindings: [{ field: temperatureField.key, channel: temperature.key }],
          },
        ],
      },
    ],
  }),
});
await task.start();
```

## Set a default or an enum mapping

The options of a field read values that its type alone cannot:

- **Default** -> the task writes the default when the response has no value for the
  field. No value means that the pointer finds nothing. Except on a JSON channel, `null`
  is also no value, and so is `""` on a channel that is not a string or bytes channel.
  With no default, the task skips the fields of the response on the field's index
  channel. See [task options](#task-options) for **NaN fill**.
- **Enum mapping** -> maps a text label in the response, such as `ON`, to a value of the
  field's type, such as `1`.

Number, string, and boolean fields have options.

1. Select the field.
2. To set a default, turn on **Optional**, then enter the **Default**.
3. To map a label, click **Add mapping** next to **Enum mapping**, then enter the
   **Label** and the **Value**.

A value that is not valid, such as text in a number field, still sends a warning. If a
request fails, the task records nothing from the endpoint, so an outage does not look
like a real reading.

## Tare channels

Tare sets the current value of a `float32` or `float64` channel to zero. The task must
be running.

1. In the endpoint list, click **Tare** on a field with a float channel. To tare several
   fields, select them, right-click, and select **Tare**.
2. The values of those channels start from zero.

## Task options

| Console label | Python field           | Default | Notes                                                            |
| ------------- | ---------------------- | ------- | ---------------------------------------------------------------- |
| Rate          | `rate`                 | 1 Hz    | Requests per second to each endpoint. One sample for each field. |
| Data saving   | `data_saving_disabled` | On      | See [data saving](/reference/hardware/tasks#data-saving).        |
| Auto start    | `auto_start`           | Off     | Starts the task each time the Driver starts.                     |

A missing or invalid field skips every field that shares its endpoint and index channel.
Turn on **NaN fill** (`nan_fill_enabled`) to write `NaN` for a missing or invalid float
field instead. It still sends a warning. A missing or invalid non-float field always
skips the group.

The task has no [stream rate](/reference/hardware/tasks#read-tasks). Each response goes
to the Core at once.

## Endpoint reference

Each setting shows its Console label, then its Python field.

| Setting                                         | Default | Notes                                                                                               |
| ----------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------- |
| Method <small>`method`</small>                  | `GET`   | `GET` or `POST` in the Console. Code accepts any method.                                            |
| Path <small>`path`</small>                      |         | Added to the base address of the server.                                                            |
| Query parameters <small>`query_params`</small>  | None    | A list of `{parameter, value}`.                                                                     |
| Headers <small>`headers`</small>                | None    | A list of `{name, value}`.                                                                          |
| Body <small>`body`</small>                      | Empty   | Sent only with methods that take a body, as `application/json`.                                     |
| Message format <small>`icd`, `messages`</small> |         | The ICD of the endpoint, the messages of it that the endpoint reads, and the channel of each field. |

The [ICD reference](/reference/hardware/icds/reference) describes the settings of a
field.

## Troubleshooting

<Problem.List>

<Problem.Item message={"endpoint ... and endpoint ... write to the same channel ..."}>
<Problem.Cause>

Two endpoints record into one channel, or into channels that share one index channel.

</Problem.Cause>
<Problem.Fix>

Give each endpoint its own channels and its own index channel.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"endpoint ... reads no messages. Open the task and pick a message for it."}>
<Problem.Cause>

The endpoint reads no ICD message. Code for an earlier version of Synnax sets `fields`
on an endpoint instead, and Synnax ignores those fields.

</Problem.Cause>
<Problem.Fix>

Create an ICD with a message for the response, then set `icd` and `messages` of the
endpoint, as the [examples](#create-an-http-read-task) do.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"Failed to read the response from ..."}>
<Problem.Cause>

The response is not JSON, or it matches more than one message. The task records nothing
from the response.

</Problem.Cause>
<Problem.Fix>

Check that the server sends JSON, and check the match rules of the messages of the
endpoint against a response from the server.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"The response from ... matches no message"}>
<Problem.Cause>

Each message of the endpoint has a match rule, and the response meets none of them. The
task records nothing from the response.

</Problem.Cause>
<Problem.Fix>

Check the match rules of the messages of the endpoint against a response from the
server.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"Field ... not found in response from ..."}>
<Problem.Cause>

The response has no value at the pointer, and the field has no default. The task skips
the fields that share its index channel, or records `NaN` for a float field when **NaN
fill** is on.

</Problem.Cause>
<Problem.Fix>

Check the pointer against a response from the server. Pointers start with `/` and are
case sensitive.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"Failed to read some data"}>
<Problem.Cause>

Some responses were missing values, or had invalid ones. The description lists each
problem. The task keeps running. See [task options](#task-options) for how an invalid
value affects the rest of its response.

</Problem.Cause>
<Problem.Fix>

Check the pointer and the data type of each field in the description against a response
from the server.

</Problem.Fix>
</Problem.Item>

<Problem.Item message={"Falling behind poll rate"}>
<Problem.Cause>

The requests take longer than one period.

</Problem.Cause>
<Problem.Fix>

Lower **Rate**, or increase **Concurrent requests** on the
[server](/reference/hardware/http/connect-server#connection-options).

</Problem.Fix>
</Problem.Item>

<Problem.Item symptom={"The task stopped while the server was down."}>
<Problem.Cause>

The task tries again for a long time, then stops.

</Problem.Cause>
<Problem.Fix>

Start the task again when the server is back.

</Problem.Fix>
</Problem.Item>

</Problem.List>

For other problems, see [Troubleshoot hardware](/reference/hardware/troubleshooting).
